# 09 — Finding Schema and Severity

**Project:** Unified VAPT Agent  
**Document:** Finding Schema and Severity Specification  
**Version:** 1.0  
**Status:** Implementation Reference

---

## 1. Purpose

This document defines the common finding structure used by the Unified VAPT Agent.

Nmap, OWASP ZAP, and Nikto produce different types of output. The application must convert their results into a consistent format so that findings can be:

- Stored in the database.
- Displayed in the dashboard.
- Compared across scanners.
- Correlated.
- Prioritized.
- Reviewed by the analyst.
- Included in the assessment report.

The normalized finding model must preserve the original scanner evidence.

The LLM may explain findings, but it must not fabricate missing finding information.

---

## 2. Finding Data Model

Every normalized finding must contain the following fields.

| Field | Type | Required | Description |
|---|---|---|---|
| finding_id | String | Yes | Unique finding identifier |
| assessment_id | String | Yes | Assessment that produced the finding |
| title | String | Yes | Short finding title |
| description | String | Yes | Finding explanation |
| target | String | Yes | Validated assessment target |
| affected_url | String or null | No | Affected URL, when applicable |
| affected_service | String or null | No | Affected service, when applicable |
| scanner | String | Yes | Scanner that produced the finding |
| scanner_finding_id | String or null | No | Original scanner finding identifier |
| severity | String or null | No | Scanner-provided severity |
| agent_priority | String or null | No | Application-assigned priority |
| confidence | String or null | No | Scanner-provided confidence |
| verification_status | String | Yes | Finding verification state |
| evidence | List | Yes | Supporting evidence |
| cve_id | String or null | No | CVE identifier, when supported |
| cvss_score | Number or null | No | CVSS score, when supported |
| remediation | String or null | No | Remediation guidance |
| detected_at | Timestamp | Yes | Finding detection time |
| last_seen_at | Timestamp or null | No | Most recent observation |
| status | String | Yes | Finding lifecycle status |

The application must use consistent field names across scanner integrations.

---

## 3. Finding Identifier

Each finding must have a unique identifier.

The identifier must:
- Be generated by the application.
- Remain stable when the finding is updated.
- Be associated with its assessment.
- Be usable for database references.

The scanner's original identifier must be stored separately.

The application must not assume that scanner finding identifiers are globally unique.

---

## 4. Scanner Attribution

The `scanner` field identifies the scanner that produced the original finding.

Allowed initial values:

- `nmap`
- `zap`
- `nikto`

The application must preserve scanner attribution during normalization and correlation.

If multiple scanners report related findings, each original scanner result must remain traceable.

The application must not replace the original scanner attribution with `llm` or `agent`.

AI-generated analysis should be stored separately from scanner-generated data.

---

## 5. Severity

Severity represents the scanner-reported or evidence-supported seriousness of a finding.

The application must distinguish severity from agent priority.

### 5.1 Severity Levels

The normalized severity levels are:

| Severity | Meaning |
|---|---|
| Critical | Scanner or supported assessment evidence indicates a critical issue |
| High | Scanner or supported assessment evidence indicates a high-severity issue |
| Medium | Scanner or supported assessment evidence indicates a medium-severity issue |
| Low | Scanner or supported assessment evidence indicates a low-severity issue |
| Informational | Observation or informational result without an assigned vulnerability severity |
| Unknown | Severity cannot be reliably determined |

### 5.2 Severity Source

Each finding should preserve the original severity information.

Suggested fields:

- `severity`
- `severity_source`
- `original_severity`

Possible severity sources:

- Scanner
- CVSS
- Application rule
- Analyst
- Unknown

The application must not silently overwrite scanner severity with an LLM-generated classification.

### 5.3 Severity Rules

The application must:

- Preserve scanner-provided severity.
- Normalize known scanner severity labels.
- Preserve original severity text.
- Use Unknown when severity is unavailable.
- Avoid inventing severity values.
- Avoid treating every scanner observation as a vulnerability.

If severity cannot be determined, the finding must remain valid with a nullable or Unknown severity.

---

## 6. Agent Priority

Agent priority represents the application's recommended order for reviewing findings.

It is separate from scanner severity.

Suggested priority levels:

- P1 — Immediate review
- P2 — High priority
- P3 — Normal priority
- P4 — Low priority
- Unassigned

The application may assign priority using a documented deterministic rule.

Possible inputs include:
- Severity.
- Verification status.
- Evidence quality.
- Exposure.
- Assessment context.

The implementation must define the actual prioritization rule before coding.

### Priority Rules

The agent must:
- Explain why a finding received its priority.
- Identify missing information.
- Preserve scanner severity.
- Avoid claiming that priority is an official CVSS score.

The agent must not silently change the priority formula.

If priority is assigned by the LLM, it must be clearly labeled as an AI recommendation and validated against the application's allowed values.

---

## 7. CVE and CVSS

### 7.1 CVE Identifier

A finding may contain a CVE identifier when the scanner or an explicitly configured trusted source provides it.

The application must:
- Preserve the source of the identifier.
- Validate the identifier's format.
- Avoid inventing CVE identifiers.
- Avoid assuming that a service version proves a CVE is present.

A matching product version alone must not automatically establish that a vulnerability exists.

### 7.2 CVSS Score

The finding may contain a CVSS score when a supported source provides it.

The application must:
- Preserve the score source.
- Preserve the original score.
- Validate that the score is within the supported range.
- Distinguish CVSS from agent priority.

The LLM must not fabricate a CVSS score.

If no supported score is available, store `null`.

### 7.3 CVSS Version

If the source provides a CVSS version, preserve it.

Suggested field:

`cvss_version`

Examples include CVSS 3.1 or CVSS 4.0.

Do not infer a CVSS version from the score alone.

---

## 8. Confidence

Confidence indicates how strongly the scanner or available evidence supports the reported finding.

Confidence must remain separate from severity.

A high-severity finding can have low confidence.

A low-severity finding can have high confidence.

### Confidence Values

Suggested normalized values:

- High
- Medium
- Low
- Unknown

The application must preserve the original scanner confidence when available.

If the scanner does not provide confidence, the application must not automatically assign High.

Any AI-assigned confidence must be labeled as an agent assessment rather than scanner confidence.

---

## 9. Verification Status

Verification status indicates whether the finding has been independently reviewed or validated.

### Allowed Values

| Status | Meaning |
|---|---|
| Potential | Scanner reported a possible issue |
| Unverified | Finding has not been independently validated |
| Confirmed | Available evidence supports the reported condition |
| False Positive | Review determined the finding does not represent the reported issue |
| Not Tested | Validation was not performed |

### Verification Rules

The application must:
- Preserve the initial verification state.
- Record changes to verification status.
- Require supporting evidence for Confirmed.
- Record the reason for False Positive.
- Avoid automatically confirming scanner findings.

The LLM must not independently mark a finding Confirmed or False Positive.

Verification changes must be controlled by application logic and authorized analyst actions.

---

## 10. Finding Evidence

Evidence is the information supporting a finding.

Each finding must have an evidence list.

### Evidence Structure

Suggested fields:

| Field | Type | Description |
|---|---|---|
| evidence_id | String | Unique evidence identifier |
| finding_id | String | Associated finding |
| evidence_type | String | Type of evidence |
| source | String | Scanner or data source |
| content | String | Evidence content or reference |
| collected_at | Timestamp | Collection time |
| raw_output_reference | String or null | Reference to stored scanner output |

### Evidence Types

Suggested values:

- Scanner Output
- HTTP Response
- Service Information
- Header
- Endpoint
- Scanner Alert
- Analyst Note
- Other

### Evidence Rules

The application must:
- Preserve the original evidence.
- Associate evidence with the correct finding.
- Record the evidence source.
- Avoid fabricating evidence.
- Distinguish scanner output from AI explanation.

The evidence content may be stored directly or through a reference to persisted raw output.

The implementation must avoid unnecessary duplication of large scanner outputs.

---

## 11. Finding Description

The finding description should explain:

- What the scanner reported.
- Where the issue was observed.
- Why it may matter.
- What evidence supports it.
- What remains uncertain.

The description must not:
- Claim exploitation occurred without evidence.
- Present a potential issue as confirmed.
- Include unsupported technical details.
- Replace scanner evidence with generated claims.

The agent may generate a readable explanation, but it must remain grounded in the finding and its evidence.

---

## 12. Remediation

The remediation field contains guidance for addressing the finding.

Remediation may be:
- Scanner-provided.
- Application-generated.
- Analyst-provided.

The application should preserve the remediation source.

Suggested field:

`remediation_source`

Possible values:

- Scanner
- Agent
- Analyst
- Unknown

### Remediation Rules

The agent must:
- Explain the recommended action.
- Avoid unsupported implementation assumptions.
- Identify when developer review is necessary.
- Distinguish recommendations from completed changes.

The application must not mark a finding as remediated merely because the agent generated a recommendation.

---

## 13. Finding Lifecycle Status

Finding lifecycle status describes the current handling state of a finding.

It is separate from verification status.

### Allowed Values

- Open
- In Review
- Accepted Risk
- Remediated
- Closed

### Status Definitions

**Open:** Finding has been recorded and requires review.

**In Review:** Finding is currently being reviewed.

**Accepted Risk:** An authorized analyst has explicitly accepted the risk.

**Remediated:** Remediation has been reported and appropriately verified.

**Closed:** Finding has been closed according to the application's workflow.

### Lifecycle Rules

The application must:
- Record status changes.
- Preserve the previous status.
- Record who or what initiated the change.
- Record the change timestamp.
- Require authorized action for analyst-controlled states.

The LLM must not independently mark findings Accepted Risk, Remediated, or Closed.

---

## 14. Finding Deduplication

The application may identify findings that appear to represent the same issue.

Deduplication must not destroy original scanner records.

### Suggested Matching Inputs

- Assessment identifier.
- Target.
- Affected URL.
- Affected service.
- Scanner finding identifier.
- Finding category.
- Evidence.
- Vulnerability identifier, when available.

### Deduplication Rules

The application must:
- Preserve original scanner findings.
- Preserve evidence from each scanner.
- Record the relationship between correlated findings.
- Avoid merging unrelated findings.
- Allow findings to remain separate when uncertainty exists.

Two findings with similar titles must not automatically be considered duplicates.

The LLM may recommend a correlation, but the application must preserve the original records.

### Correlation Record

Suggested fields:

- correlation_id
- finding_ids
- correlation_reason
- correlation_method
- created_at

The correlation method should distinguish deterministic matching from AI-recommended matching.

---

## 15. Finding Updates Across Assessments

When a later assessment reports a similar issue, the application may associate it with a historical finding.

The application must distinguish:

- Newly detected finding.
- Previously detected finding.
- Finding observed again.
- Finding not observed in the latest assessment.
- Finding not retested.

Absence from a scanner report does not automatically prove remediation.

A finding should only be marked Remediated when the application's remediation workflow has sufficient verification evidence.

---

## 16. Database Persistence

The normalized finding must be stored in the application's database.

The persistence layer must:
- Store required fields.
- Support nullable optional fields.
- Preserve evidence references.
- Preserve scanner attribution.
- Preserve verification status.
- Preserve lifecycle status.
- Support assessment-level retrieval.

The finding schema must align with the Backend Schema document.

Database updates must not rely on the LLM to generate SQL.

All database writes must use the application's validated persistence layer.

---

## 17. Dashboard Requirements

The dashboard should display:

- Finding title.
- Target.
- Scanner.
- Severity.
- Agent priority.
- Verification status.
- Lifecycle status.
- Detection time.

The finding detail view should display:

- Description.
- Evidence.
- Scanner source.
- CVE information, when available.
- CVSS information, when available.
- Remediation.
- Verification history.
- Correlation information.

The dashboard must clearly distinguish:

- Scanner severity.
- Agent priority.
- Verification status.
- Lifecycle status.

These fields must not be combined into a single ambiguous label.

---

## 18. Report Requirements

The final report must include:

- Finding title.
- Affected target.
- Scanner source.
- Severity.
- Agent priority, if assigned.
- Verification status.
- Evidence.
- CVE and CVSS information, if available.
- Remediation recommendation.
- Relevant limitations.

The report must preserve uncertainty.

Potential findings must not be presented as confirmed vulnerabilities.

The report must not claim that the assessment proves the target is secure.

---

## 19. MVP Acceptance Criteria

The finding model is acceptable when:

1. Findings from Nmap, ZAP, and Nikto can be normalized.
2. Each finding has a unique application identifier.
3. Scanner attribution is preserved.
4. Original scanner identifiers are preserved when available.
5. Severity is stored separately from agent priority.
6. Verification status is stored separately from lifecycle status.
7. Evidence is associated with the finding.
8. Missing CVE information remains missing.
9. Missing CVSS information remains missing.
10. Findings can be correlated without deleting original records.
11. Finding status changes are auditable.
12. The dashboard displays finding information accurately.
13. The report preserves evidence and uncertainty.
14. The LLM cannot fabricate or directly persist unsupported findings.

---

## 20. Final Design Principle

The normalized finding model must preserve the difference between:

**What the scanner observed, what the evidence supports, what the agent recommends, and what the analyst has verified.**

These are separate concepts.

Keeping them separate is essential for producing trustworthy vulnerability assessment results.
